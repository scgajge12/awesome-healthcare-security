# 医療機関向け防御プレイブック

[ランサムウェアグループの TTPs](ransomware-groups.md) と、国内外の[インシデント事例](../incidents/)から導かれる対策を、優先順位をつけて整理する。

> [!NOTE]
> **表記ルール**：本ページでは、**事実**（一次情報で確認できる内容。出典を併記する）、**報道ベース**（報道のみで確認でき、当事者の公表資料では裏付けが取れていない内容）、**分析**（筆者の解釈）を書き分ける。
> 出典は、当事者の公表資料、行政文書、CVE、ベンダアドバイザリなどの一次情報を優先して示す。

> [!TIP]
> すべてを同時に実施できる医療機関は少ない。
> 本ページは、限られた予算と人員で何から着手するかを判断するための順序として構成している。

## 攻撃の流れと防御段階の対応

各段階が、攻撃のどこを断つためのものかを示す。

```mermaid
flowchart LR
    subgraph attack["攻撃の流れ"]
        direction TB
        A1["初期侵入"] --> A2["権限昇格と探索"]
        A2 --> A3["水平展開"]
        A3 --> A4["バックアップの破壊"]
        A4 --> A5["暗号化"]
        A5 --> A6["診療の停止"]
    end

    D1["第 1 段階<br>侵入口を塞ぐ"] --> A1
    D2["第 2 段階<br>広がりを止める"] --> A3
    D3["第 3 段階<br>復旧できる状態を作る"] --> A4
    D4["第 4 段階<br>気付けるようにする"] --> A2
    D5["第 5 段階<br>止まったときに動けるようにする"] --> A6
```

## 第 0 段階：現状を知る

対策の前に、守るべき対象と現在の状態を把握する必要がある。

- [ ] 外部からアクセスできる資産を洗い出す（VPN 装置、公開サーバ、リモートデスクトップ、PACS）
- [ ] 外部と接続している事業者を洗い出す（給食、検査、保守、地域連携、クラウド）
- [ ] 医療機器の台帳と IT 資産台帳を突き合わせる
- [ ] バックアップの構成と、実際に復旧できるかを確認する
- [ ] 厚生労働省の[サイバーセキュリティ対策チェックリスト](../../guidelines/japan.md)を埋める

現状把握のない対策投資は、たいてい効かない場所に向かう。

---

## 第 1 段階：侵入口を塞ぐ

国内外の公表済み事例で、初期侵入経路として繰り返し確認されている箇所である。
費用対効果が最も高い。

| 対策 | 内容 | 対応する事例 |
|---|---|---|
| **境界機器のパッチ適用** | VPN 装置、ゲートウェイ、リモートアクセス製品を最優先で更新する。EOL 製品は交換する | 半田病院、デュッセルドルフ大学病院 |
| **すべてのリモートアクセスへの MFA 適用** | 例外を作らない。委託先アカウント、保守アカウントも対象にする | Change Healthcare |
| **リモートデスクトップの直接公開の停止** | インターネットから RDP に到達できる状態を解消する | 多数 |
| **委託先接続の見直し** | 接続元, 接続先, 期間, 権限を必要最小限に限定する。常時接続を必要時開放に変える | 大阪急性期, 総合医療センター |
| **漏えい認証情報の監視** | 自組織のドメインの認証情報が流通していないか継続的に確認する | 多数 |

> [!IMPORTANT]
> Change Healthcare の事例では、多要素認証が設定されていないリモートアクセスアカウントが起点になったことが議会証言で明らかにされている。
> 全米規模の医療インフラ停止の起点が、この一点だった。

### 多要素認証は、どこで漏れるか

「リモートアクセスに多要素認証を適用した」と説明される構成でも、適用の外に置かれる入口が残る。
残りやすい箇所を挙げる。

| 残りやすい箇所 | なぜ残るか |
|---|---|
| 境界機器のローカルアカウント | ID 基盤の障害時に備えた非常用として作られ、多要素認証の対象から外れる |
| 保守ベンダのアカウント | 契約上、ベンダ側の運用に合わせるため、自組織の認証方針が及ばない |
| サービスアカウント、連携用アカウント | 対話的なログインを想定しないため、多要素認証を適用できない |
| 古い認証プロトコル | 多要素認証に対応しない方式が有効なまま残り、そちらを使えば回避できる |
| 例外として登録されたアカウント | 導入時に業務影響を避けるため除外され、そのまま恒久化する |

**分析**：適用の網羅を確認する作業は、設定画面で「有効」を見ることではなく、**多要素認証を経ずにログインできたアカウントが期間内に存在したか**をログから数えることになる。
除外の一覧を作り、除外ごとに、接続元の限定、資格情報の個別化、監視の追加のいずれかを代償措置として置く。

### 境界機器は、パッチを当てても侵害前には戻らない

境界機器の脆弱性が公表されたとき、対応はパッチの適用で終わらない。
悪用がすでに起きていた場合、機器に残るものが次に使われる。

- 機器が保持していた資格情報と証明書は、失効させる。設定のバックアップから復元すると、同じ資格情報が戻る
- 接続していた利用者のセッションと、発行済みのトークンを無効化する
- 設定に追加された可能性のある項目（アカウント、スクリプト、転送先、認証の除外）を、既知の正しい構成と突き合わせる
- ベンダが公表している侵害の痕跡の確認手順があれば、それに沿って確認する

**分析**：境界機器は、侵害されたときに最も痕跡を確認しにくい部類に入る。
機器の中で何が起きたかを調べる手段が限られ、ログの保存も短い。
そのため、悪用が公表された脆弱性については、**侵害されていない証明ではなく、侵害されていた前提での資格情報の入れ替え**を先に済ませるほうが早い。

## 第 2 段階：広がりを止める

侵入を完全に防ぐことはできない。
被害を局所化できるかどうかが、診療停止期間を決める。

| 対策 | 内容 |
|---|---|
| **ネットワークの分離** | 医療機器、電子カルテ、事務系、来客用 Wi-Fi を分離する。医療機器セグメントからのインターネット直接アクセスを禁止する |
| **管理者権限の最小化** | 日常業務に管理者権限を使わない。特権アカウントを専用端末に限定する |
| **ローカル管理者パスワードの個別化** | 同一パスワードの使い回しを解消する（LAPS 等の仕組みを利用する） |
| **仮想化基盤の保護** | ESXi などのハイパーバイザ管理インタフェースを分離し、多要素認証を適用する。ここが落ちると全システムが同時に停止する |
| **不要なプロトコルの停止** | SMBv1、LLMNR, NBT-NS など、水平展開に使われる古い機能を無効化する |

この段階の対策は、実施したかどうかではなく、到達できなくなったかどうかで確認する。
ゾーンの切り方、分離が破れる典型的な構造、到達性の確認手順は [ネットワークの分離](../../technology/segmentation.md) に整理している。

### 医療機関の Active Directory で、権限が集まりやすい箇所

水平展開は、到達性と資格情報の両方が揃ったときに成立する。
資格情報の側は、医療機関では次の形で集まりやすい。

| 箇所 | どう成立するか | 確認と置き換え |
|---|---|---|
| 部門システムのサービスアカウント | ベンダの導入手順書が、動作確認を優先して広い権限を指定している | 実際に必要な権限まで下げる。下げられない場合は、そのアカウントでログオンできる範囲を限定する |
| ベンダの保守アカウント | 保守のたびに申請するのは運用に合わないとして、恒久的な特権が付与される | 期限付きで権限を渡す形に変える。渡した期間と操作を記録する |
| 医療機器に付属する PC | 承認済み構成のため設定を変えられず、ドメインに参加したまま EDR の対象から外れる | ドメイン参加の要否を確認する。参加が要るなら、その端末から到達できる範囲を絞る |
| 共有端末に残る資格情報 | 多職種が交代で使うため、ログオンしたままの状態が続く | 画面ロックと自動ログオフを、診療の妨げにならない範囲で設定する。特権アカウントを共有端末で使わない |
| バックアップ基盤 | 運用の簡便さから、業務ドメインの認証をそのまま使う | 認証を分離する。第 3 段階の前提になる |
| 仮想化基盤の管理者 | 電子カルテを含む基幹が集約され、管理者が全システムに等しく到達する | 管理インタフェースを分離し、多要素認証を適用する |

**分析**：この表の各行は、いずれも運用上の理由から生まれている。
権限を下げる提案が現場に通らない場合、権限そのものではなく、**その資格情報でログオンできる端末とゾーンを絞る**側に手を入れると、実現できることが多い。
実際に到達できるかどうかは、侵入前提の検証で測れる（[診断とペネトレーションテスト](../../practice/pentest/)）。

> [!WARNING]
> 分離を先に強めると、業務で使われていた経路を予告なく塞ぐことがある。
> 検査結果が届かない、画像が参照できないといった形で診療に出るため、遮断の前に、その経路が実際に使われていないことを測る。

## 第 3 段階：復旧できる状態を作る

バックアップは「取っている」ことではなく「戻せる」ことに意味がある。

- [ ] バックアップの少なくとも 1 系統をオフラインまたはイミュータブル（変更不可）で保管する
- [ ] バックアップ基盤の認証を、業務ドメインから分離する
- [ ] 実際にリストアする訓練を、年 1 回以上実施する
- [ ] 電子カルテの復旧に要する時間を実測し、その時間だけ紙運用に耐えられるかを検証する
- [ ] 復旧の優先順位を、診療への影響度に基づいて定義する

医療機関のランサムウェア被害では、バックアップも同時に暗号化されていた事例が繰り返し報告されている。
バックアップ基盤が業務ドメインの認証を使っている限り、ドメイン管理者を奪われた時点で一緒に失われる。

## 第 4 段階：気付けるようにする

暗号化までには数日から数か月の潜伏期間がある。
この間に検知できれば、被害は回避できる。

検知の設計は、「何を見たいか」だけでは実装できない。
その事象がどのログに現れるかを決めて初めて、機器の設定と保存期間の話になる。

| 監視対象 | 検知したい事象 | 観測点（どこから取るか） |
|---|---|---|
| 認証 | 業務時間外のログイン、通常と異なる場所からのアクセス、認証失敗の急増 | ドメインコントローラの監査ログ、VPN とリモートアクセスゲートウェイの認証ログ、ID 基盤のサインインログ |
| 特権操作 | 新規の管理者アカウント作成、特権グループへの追加、委任設定の変更 | ドメインコントローラの監査ログ、特権管理製品の操作記録 |
| ツール | 業務で使っていないリモート管理ツールの実行と通信 | EDR のプロセス実行記録、プロキシとファイアウォールの宛先ログ |
| セキュリティ製品 | ウイルス対策, EDR の停止、定義更新の停止、除外設定の追加 | 各製品の管理サーバが持つ稼働状況と設定変更の記録 |
| 内部通信 | 短時間での大量スキャン、通常と異なるサーバ間通信 | ゾーン境界のファイアウォールの拒否ログ、通信フローの記録（[ネットワークの分離](../../technology/segmentation.md)） |
| 外向き通信 | 大量のデータ転送、未知のクラウドストレージへの通信 | プロキシのログ、境界ファイアウォールの転送量、DNS の問い合わせ記録 |
| バックアップ | シャドウコピーの削除、バックアップジョブの異常終了、基盤への異常なログイン | バックアップ基盤の認証ログとジョブ記録、サーバのシステムログ |
| 仮想化基盤 | 管理インタフェースへのログオン、仮想マシンの一括停止 | ハイパーバイザ管理基盤の監査ログ |
| 電子カルテ | 1 人の利用者が短時間に参照した患者数の急増、業務時間外の一括出力 | 電子カルテと部門システムの監査ログ（[患者用ポータルで狙われやすい脆弱性](../../technology/web-security/patient-portal.md#7-検知ポータル側で何を見れば気付けるか)） |
| 保守回線 | 開放記録のない時間帯の接続、接続元アドレスの変化 | 保守用踏み台の接続ログ、開放申請の記録（[IoMT のリスク](../../technology/medical-devices/iomt.md)） |

**分析**：この表の右列が空欄のまま残ると、検知の設計は文書の上で完結する。
医療機関で埋まりにくいのは、電子カルテと部門システムの監査ログ、保守回線の接続ログの二つである。
前者はベンダの製品仕様に依存し、後者はメーカーの管理範囲に置かれるため、いずれも自組織の設定だけでは取得を決められない。
調達と保守契約の更新が、実際の取得の契機になる。

### 保存期間を、潜伏期間に合わせる

侵入から暗号化までの潜伏期間が数週間から数か月に及ぶことは、この段階の前提である。
ログの保存期間がそれより短いと、侵入経路と侵害範囲を確定できないまま復旧を始めることになる。

- 認証、特権操作、外向き通信のログは、少なくとも侵入経路の調査に足りる期間を保持する
- ログの保管先を、業務ドメインの認証から分離する。攻撃者が管理者権限を得た時点で消せる場所に置かない
- 保管しているだけで見ていない状態を、取得できている状態と区別する

専任者を置けない場合、監視の外部委託（MDR, SOC サービス）を検討する。
検知の仕組みだけ導入して、通知に対応する人がいない状態が最も危うい。

## 第 5 段階：止まったときに動けるようにする

医療機関の事業継続計画は、「システムが 1 か月使えない」という前提で作る必要がある。

### ダウンタイム手順

- [ ] 紙運用への切り替え手順を、部門ごとに文書化する
- [ ] 紙の帳票と、検査依頼書, 処方箋の予備を確保する
- [ ] 過去の診療情報を参照する代替手段を用意する（定期的な紙, PDF 出力など）
- [ ] 訓練を実施する。文書があるだけでは動けない

### インシデント対応体制

- [ ] 初動の判断者と、意思決定の流れを定義する
- [ ] 外部の支援先（フォレンジック事業者、ベンダ、JPCERT/CC、医療 ISAC）の連絡先を事前に確保する
- [ ] 所轄官庁, 個人情報保護委員会への報告要件と期限を確認する
- [ ] 患者, 家族, 報道機関への広報方針を事前に定める
- [ ] 地域の医療機関との連携（患者の受け入れ, 転送）を協定として準備する

### 身代金を支払うかの判断

支払いの是非は、経営判断として事前に方針を定めておくべき事項である。
インシデント発生後に、混乱の中で初めて議論する状態は避けたい。
検討にあたっては次を踏まえる必要がある。

- 支払っても、復号ツールが正常に機能する保証はない
- 支払っても、窃取されたデータが削除される保証はない
- 制裁対象の組織への支払いは、法令上の問題を生じうる
- 国内外の公表事例では、身代金を支払わずに再構築を選んだ医療機関が複数ある
